# Lumae Security Audit

**Scope.** This is an evidence-based review of the current repository and public deployment at `https://lumae.co.in`, mapped to the 36 checks supplied by the owner. It did not modify production data, infrastructure, identities, connected accounts, or payment configuration. A status of **UNKNOWN** means the control could not be proved from repository access and non-invasive public checks; it is not a pass.

## Executive summary

The deployment presents a meaningful baseline of security controls: HTTPS, HSTS, restrictive production CSP, no public debug routes, server-side authentication/authorization middleware, signed sessions, bounded body sizes, and targeted rate limits were confirmed. The focused security/auth/payment test set also passed **73 tests across 8 files**.

However, there are several material findings that should be addressed before relying on automated payments or treating storage paths as private access controls. The highest priority issues concern payment ownership/amount binding, unrestricted storage-key presigning, an SSRF-capable transcription URL, CSRF handling when `Origin` is absent, and sensitive Razorpay webhook logging.

| Priority | Finding | Why it matters |
|---|---|---|
| P0 | Payment verification does not bind the provider payment/session to the authenticated user, expected order, or selected package. | A valid payment reference could be replayed or paired with a more valuable package. |
| P1 | The public storage proxy presigns an arbitrary requested storage key. | A guessed or disclosed private object key can be turned into a downloadable URL. |
| P1 | Transcription accepts an unrestricted server-side `audioUrl`. | An attacker could cause the server to request internal or cloud-metadata addresses. |
| P1 | Razorpay webhook logging includes customer email and payment details. | Sensitive customer data is retained in operational logs. |
| P1 | Browser state changes rely on `Origin` only when it is supplied, while secure cookies use `SameSite=None`. | A request without an `Origin` header avoids the origin rejection branch. |

## Recommended remediation sequence

1. **Pause direct payment crediting until ownership, order, amount, package, and idempotency validation are server-side.** Remove the exposed placeholder monetization router or make it explicitly non-production. Then repair Razorpay’s raw-body webhook verification and log redaction.
2. **Restrict the storage proxy and transcription input.** Private storage should be fetched only by an ownership-checked endpoint; transcription should only read a server-generated managed storage URL/key.
3. **Strengthen browser request and session controls.** Enforce trusted Origin/Referer on all state-changing cookie-authenticated routes, eliminate the one-year SDK fallback, and make OAuth logout revocable.
4. **Perform credential hygiene.** Remove browser-side key-looking fixture strings, privately inspect the identified historical commit, rotate any real secret found, and enable repository/CI secret scanning.
5. **Complete the controls marked UNKNOWN.** Review database IAM/grants, storage bucket policy, CI log masking, deployment access control, shared rate limiting, and provider defaults.

## Verification record

The review used read-only repository inspection, tracked-file and value-safe Git-history scans, non-invasive public HTTP header/path probes, and focused existing tests. The following security-focused tests passed during the audit: `server/security.regression.test.ts`, `server/auth.logout.test.ts`, `server/localAuth.regression.test.ts`, `server/twoFactor.regression.test.ts`, `server/webhook.test.ts`, `server/monetization.test.ts`, `server/razorpay.credentials.test.ts`, and `server/socialConnectAutomation.regression.test.ts` (**73 tests**).

No penetration test, credential rotation, database grant review, cloud bucket policy review, browser-authenticated CSRF test, or production payment was performed. Those boundaries explain the **UNKNOWN** classifications above.
